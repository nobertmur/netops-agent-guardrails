# netops-agent-guardrails

A small network-operations agent built around one idea: **an agent may suggest, but a policy gate decides.**
It detects problems in telemetry, proposes fixes (with rules or an LLM), and then every proposal
passes an allowlist, risk rules, limits, human approval and a tamper-evident audit log before
anything is even simulated.

> **Status: reference project.** Telemetry is simulated, the detectors are simple statistical
> baselines, and no executor logs in to a device. The guardrail logic is the real content and is
> covered by 68 tests, including attempts to abuse it.

## See it work

```bash
make setup
make demo       # deterministic simulated incident
make verify     # check the audit log's hash chain
```

The simulated incident produces four findings. The policy treats the resulting proposals differently:

| Proposal | Device | Policy verdict | Why |
| --- | --- | --- | --- |
| `open_ticket` (x4) | all four | allowed automatically | low risk, changes nothing |
| `shutdown_interface swp1` | leaf01 | needs a human | high risk |
| `clear_bgp_soft swp2` | leaf02 | needs a human | medium risk |
| `shutdown_interface swp2` | spine01 | **denied** | high risk on a protected device becomes critical |
| (telemetry row `swp1; reboot`) | leaf01 | **dropped at load** | unsafe identifier |

With the default approver (`deny`) nothing that changes a device runs. Use `--approver interactive`
to be asked at the terminal, and `--executor proposal-files` to write each approved change as a
YAML file for a pull request instead of a dry-run record.

## Architecture

```
 telemetry -> detect -> findings -> propose -> POLICY -> approve -> execute
                                    (rules|LLM)  (risk,    (human,    (dry-run /
                                    untrusted     limits,   digest-    proposal file)
                                                  window)   bound)
   every step appended to a hash-chained audit log
```

| Module | What it does |
| --- | --- |
| `telemetry.py` | Loads samples; rejects unsafe names and unknown metrics |
| `detect.py` | Interface error thresholds, BGP flap counting, latency z-score. Each finding carries its evidence |
| `proposer.py` | `RuleProposer`, and `LLMProposer` that accepts only strictly structured JSON |
| `policy.py` | Allowlist, parameter patterns, protected devices, change window, rate limits |
| `approval.py` | Approvals bound to a SHA-256 of the exact change |
| `executor.py` | Re-checks the approval; dry-run or proposal-file output |
| `audit.py` | Append-only hash chain; detects edit, delete and reorder |

## Guardrails at a glance

- **Allowlist.** Actions not in `policy.yml` are denied: no reboots, no arbitrary CLI.
- **Parameter patterns.** `swp1; reload` fails the full-match regex for `interface`.
- **Risk is policy-owned.** A proposer cannot declare its own change safe.
- **Protected devices.** One risk level higher; high becomes critical, which is denied.
- **Limits and window.** Per run, per device per hour (counted across runs), and a UTC change window.
- **Human approval bound to the change.** An approval for one change cannot unlock another.
- **LLM output is untrusted.** Strict schema, capped and sanitised rationale, device taken from the finding.
- **Audit.** Every finding, decision, approval and execution is chained; `verify` names the first broken record.

The full threat model, with the test that covers each threat, is in [docs/design.md](docs/design.md).

## Using an LLM proposer

```python
from netops_agent.proposer import LLMProposer

proposer = LLMProposer(complete=my_model_call, allowed_actions=list(policy.actions))
```

`my_model_call(prompt: str) -> str` is any function that returns the model's text. No provider
SDK is required, and the tests use fakes, including a hostile one that asks for a reboot.

## Project layout

| Path | Purpose |
| --- | --- |
| `netops_agent/` | The package |

| `samples/incident.json` | Simulated telemetry, generated by `scripts/generate_samples.py` |

## Limits and next steps

- Detectors are baselines, not trained models; remediation rules are illustrative.
- The audit chain detects tampering but does not prevent it; ship logs to write-once storage.
- A production executor should open a pull request in the config repository
  (see `network-automation-pipeline`) rather than touch devices directly.
- Next: real telemetry sources (SNMP, gNMI, Prometheus), an approval channel in chat or ticketing,
  and replaying recorded incidents to measure false positives.
